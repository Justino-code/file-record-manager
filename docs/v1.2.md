File Record Manager — v1.2

Overview

Version 1.2 is a refactoring version of the initial File Record Manager implementation.

The purpose of this version is not to introduce new functionality, but to improve the existing implementation while preserving its behavior.

The main focus is code organization, consistency, readability, and reducing unnecessary duplication.

Objective

The objective of v1.2 is to review the v1 implementation and make justified improvements without introducing concepts that belong to later versions.

The guiding principle is:

«Refactor only when there is a clear reason to do so.»

The project should remain functionally equivalent to v1 after the refactoring.

Scope

The following areas are within the scope of v1.2:

- Code simplification
- Removal of duplicated logic
- More consistent use of existing helper functions
- Improved readability
- Consistent type usage
- Improved file-positioning operations where appropriate
- Identification of design issues for future versions

The following are intentionally outside the scope:

- Dynamic memory allocation
- New data structures
- Major architectural redesign
- New application features
- Advanced pointer-based designs

Refactoring of "lAdd"

The original "lAdd()" contained logic for creating and collecting the data of a new book.

The creation logic was extracted into "lCreate()".

This allows "lAdd()" to focus primarily on the file-related responsibility of adding the record.

The file-size logic was also extracted into a separate "fileSize()" function.

This resulted in a simpler responsibility structure:

lAdd()
 ├── determine the next ID
 ├── create the record
 └── write the record

The refactoring was committed as:

refactor: extract file size logic and simplify lAdd

Refactoring of "lList"

"lList()" was simplified through several small consistency improvements.

The code now uses the "Livro" typedef directly instead of repeatedly writing:

struct Livro

File positioning was also simplified by using:

rewind(fp);

instead of:

fseek(fp, 0, SEEK_SET);

The size expression was also standardized to:

sizeof(Livro)

The refactoring was committed as:

refactor: simplify lList type and file positioning

Refactoring of "lSearch"

"lSearch()" previously handled input using "fgets()" directly and manually removed the newline character.

Since the project already provides "readLine()", the search function was changed to use the existing helper:

readLine(titulo, sizeof(titulo));

The duplicated newline-removal logic was therefore removed.

This change centralizes line input handling and avoids repeating functionality already provided by "readLine()".

The refactoring was committed as:

refactor: use readLine in lSearch

Functions Reviewed Without Changes

Some functions were reviewed but did not present a sufficiently strong reason for modification.

These include:

- "show()"
- "lCreate()"
- "readLine()"
- "readInt()"
- "lRemove()"

The decision not to modify these functions is intentional.

Refactoring is not about changing code simply to make it different. A function that is already sufficiently clear and correct does not need to be changed.

File Cursor Behavior

During the refactoring process, an architectural concern was identified regarding file cursor positioning.

Different functions currently leave the "FILE *" cursor in different positions.

For example:

- "lList()" starts from the beginning and normally reaches the end of the file.
- "lSearch()" starts from the beginning and leaves the cursor immediately after a matching record.
- "lAdd()" works toward the end of the file.
- "lUpdate()" and "lRemove()" currently depend on the position left by "lSearch()".

This creates implicit coupling between functions.

The issue was identified but intentionally not redesigned during v1.2.

A future version should define clearer contracts for file cursor positioning.

// TODO: Define a standard contract for the final file cursor
// position in functions that manipulate FILE *.

Architectural Observation

During the refactoring, an important conceptual distinction was identified:

1. File manipulation
2. Record manipulation

The current implementation mixes these responsibilities.

For example, functions such as "lUpdate()" know both how a "Livro" is manipulated and how the underlying file is positioned and modified.

This is acceptable for the current educational stage, but it is an important candidate for architectural improvement in a future version.

Version Documentation Decision

A decision was made to document the project version by version.

Each major or incremental version will have documentation describing the state of the project at that point in its evolution.

The documentation may include:

- Objectives of the version
- Changes made
- Design decisions
- Architectural decisions
- Concepts introduced
- Known limitations
- Problems identified for future versions
- Planned directions, when applicable

The version documentation is intended to preserve not only what the code became, but also why it evolved that way.

The general project README will remain focused on the overall project, while version-specific documentation will preserve the history and reasoning behind each version.

The planned structure is:

docs/
├── v1.md
├── v1.2.md
└── v2.md

Future versions should add their own documentation when appropriate.

Version Philosophy

Version 1.2 deliberately avoids introducing new concepts just for the sake of making the code more sophisticated.

The purpose is to make the existing implementation as clear, predictable, and correct as possible before introducing a new level of complexity.

Version Status

The v1.2 refactoring is considered complete once the existing operations have been tested to ensure that the refactoring did not introduce behavioral regressions.

After validation, v1.2 can be merged into "main" as the next stable version.

The next major evolution will take place in v2.
