File Record Manager — v2

Overview

Version 2 is planned as the next major evolution of the File Record Manager.

Unlike v1.2, which focuses on refactoring without changing the project's fundamental design, v2 will introduce new C programming concepts and begin evolving the internal architecture of the system.

The version will be developed incrementally, with particular attention to understanding the relationship between pointers, memory, records, and file storage.

Main Objectives

The main objectives of v2 are:

- Introduce more extensive use of pointers.
- Introduce dynamic memory allocation where appropriate.
- Improve the representation of records.
- Begin separating file manipulation from record manipulation.
- Explore a more flexible architecture for storing records.
- Preserve the project as a practical environment for studying C.

The objective is not simply to add complexity, but to introduce each concept where it solves a real limitation of the current implementation.

Planned Concepts

The main concepts planned for this version include:

- Pointers
- Pointer-based data manipulation
- Dynamic memory allocation
- "malloc()"
- "free()"
- Memory ownership
- Lifetime of dynamically allocated data
- More flexible data representation
- Separation of responsibilities

The concepts will be introduced gradually rather than all at once.

From Fixed Records to Flexible Records

The current "Livro" structure uses fixed-size fields:

struct Livro {
    int id;
    char titulo[100];
    struct Autor autor[3];
    int a_len;
    int ano;
};

This design is intentionally simple, but it also imposes limitations.

For example:

- A title is limited to 99 characters.
- An author name is limited to 99 characters.
- A book can contain at most three authors.
- Every record reserves space for the maximum number of authors.

Dynamic memory provides an opportunity to investigate more flexible representations.

A possible future direction is to replace fixed-size arrays with dynamically allocated memory.

This will be explored as part of the v2 development rather than assumed as the final design from the beginning.

File Manipulation vs. Record Manipulation

One of the main architectural observations carried from v1.2 is that two different concepts are currently mixed together.

File manipulation

This concerns operations such as:

fopen
fclose
fread
fwrite
fseek
ftell
rewind

These operations deal with storing and retrieving bytes from a file.

Record manipulation

This concerns operations such as:

create a book
search for a book
update a book
remove a book
display a book

These operations deal with the meaning and structure of the data.

The current implementation combines both responsibilities.

For example, "lUpdate()" understands both the "Livro" structure and the position of that record inside the file.

Planned Architectural Direction

The v2 architecture will investigate separating these concerns.

Conceptually, the goal is to move toward something similar to:

                Application / Domain
                        │
                     Record
                        │
              ┌─────────┴─────────┐
              │                   │
       Record operations     File storage
              │                   │
         Livro/other          FILE *
         structures        fread/fwrite/fseek

The exact architecture will be determined during implementation.

The important principle is that the mechanism responsible for storing data should not unnecessarily depend on the specific meaning of that data.

This would make it easier to imagine the same storage mechanisms being used with other record types in the future.

Pointers and Dynamic Memory

Pointers are not being introduced solely because they are more advanced.

They will be introduced because they become useful when the project begins working with data whose size or lifetime cannot be adequately represented using fixed-size arrays.

Dynamic memory allocation will be introduced where it provides a concrete benefit.

For example, a dynamically allocated string could allow a record to use memory proportional to the actual size of its contents rather than reserving a fixed-size character array.

However, the project will prioritize understanding memory ownership and lifetime before introducing unnecessary dynamic allocation.

Incremental Development

The v2 development will be incremental.

A possible progression is:

v2
 └── Introduce pointers where they clarify the design

v2.1
 └── Introduce dynamic memory where appropriate

v2.2
 └── Improve record/file separation

Future versions
 └── Introduce additional data structures or storage concepts

This is a development direction rather than a fixed implementation specification.

The exact version boundaries may change as the project evolves.

Compatibility With the Learning Objective

The project remains primarily educational.

The purpose of v2 is not to build the most sophisticated record-management system possible.

Instead, each architectural change should provide an opportunity to understand a C programming concept in a realistic context.

The project should therefore avoid abstractions that cannot yet be justified or understood.

Expected Challenges

The main challenges expected in v2 include:

- Understanding pointer ownership.
- Avoiding memory leaks.
- Avoiding invalid memory access.
- Managing dynamically allocated strings.
- Understanding the lifetime of records in memory.
- Deciding where allocation and deallocation should occur.
- Keeping file storage independent from record representation.
- Maintaining predictable file cursor behavior.

These challenges are considered part of the learning objective of the version.

Version Status

Version 2 is planned and has not yet been implemented.

The design described in this document represents the current direction of development and may be revised as implementation and experimentation reveal better solutions.
